# Capability matrix

This document is the working definition of logical parity for Orleans.Dataflow. It tracks capabilities and semantics, not API spelling or implementation similarity.

Akka.NET Streams is the reference for the general streaming model. Microsoft Orleans and .NET documentation define the constraints of Orleans-native adapters. An item is not complete merely because a method with a similar name exists.

## Status vocabulary

- **Research**: semantics are understood and linked, but no contract is approved.
- **Specified**: public and runtime semantics are documented and reviewed.
- **Implemented**: code and focused tests exist.
- **Qualified**: contract, failure, and integration tests prove the documented behavior.
- **Deferred**: intentionally outside the current milestone, with a recorded reason.

Every row starts at **Research** and advances only together with its evidence; Implemented rows have code and focused tests on `main`.

## Capability tiers

- **P0**: required to call the result a bounded dataflow runtime at all.
- **P1**: required for the C# logical-parity gate.
- **P2**: expected before or shortly after 1.0, depending on evidence and package boundaries.

## Graph and materialization

| Capability | Tier | Target | Status | Required semantic proof |
|---|---:|---:|---|---|
| Immutable typed source, flow, and sink blueprints | P0 | M0 | Implemented | Composition does not execute work; instances are thread-safe and reusable. |
| Reusable `Flow<TIn,TOut>` composition | P0 | M0 | Implemented | Reusing one fragment creates independent node identities and runtime state. |
| Closed runnable graphs | P0 | M0 | Implemented | Validation can distinguish open ports from a materializable graph. |
| Named graph, stage, port, and revision identity | P0 | M0 | Implemented | Deterministic serialization, collision checks, and compatible revision rules. |
| Runtime materialization | P0 | M2 | Implemented | Each run allocates independent runtime resources and exposes completion. The document and the binding table are required to describe the same node since M4.1 checkpoint 5, which closes checkpoint 2's recorded gap: the stage a node declares is compared with the stage its binding's kind declares, so a `merge` bound to a zip, a `select` bound to a where, or a `first` bound to a last is refused instead of executing the binding while the fingerprint goes on describing the document. The check is asked **last**, after every structural refusal — a node fed by two streams that is not a fan-in, a junction wired at a port its stage does not declare, a shape that cannot stand where the document puts it — because those name what the runtime actually cannot do and are sharper; what reaches the new check is the residue nothing structural could separate. It is unreachable through the authoring API, which builds the node from the binding's own kind. |
| Typed result slots | P1 | M2 | Implemented | Source, flow, sink, and lifecycle results are declared as typed named slots and resolved per run without persisting runtime objects; a run rejects slots from another graph identity, revision, or import scope. |
| Named multiple results | P1 | M4 | Implemented | Results remain type-safe and versionable across distributed execution. Since M4.2 a graph declares one result per result-bearing branch: the branch names its own slot where its sink is written, the document declares that name against the branch's own terminal, and one run resolves every one of them independently (`JunctionAuthoringTests`, `FluentJunctionTests`). Two branches under one name are refused by the document's own uniqueness rule, which this surface reaches for the first time — a linear graph is closed by one `To` carrying at most one name. The typing is the C# compiler's, as it is for every local graph: a slot carries `TResult` from the sink that declared it. A branch's slot is the one slot that exists before its graph does, because a branch is written as an argument of the junction call that consumes it; it names its graph from that call onwards, reading it earlier throws rather than answering with a fingerprint of nothing, and a branch that declares a result closes exactly one graph instead of repointing the first graph's slot. **The distributed half is not proven and cannot be yet**: a junction is a local stage, so every multi-result graph is `nondeployable` and no cluster test exercises one. |
| Explicit fan-in/fan-out graph construction | P1 | M4 | Implemented | All ports are connected exactly once unless a junction contract states otherwise. The M4.2 authoring surface (ADR 0006) spells every junction the M4.1 engine runs: `BroadcastTo`, `BalanceTo`, `PartitionTo`, `UnzipTo`, and `AlsoTo` take branches and close the graph the way `To` closes a chain; `Merge`, `Concat`, `Interleave`, `Zip`, and `CombineLatest` join sources and return one; `Fork`/`ForkMerge` carry the diamond a tree cannot express. A port is connected exactly once by construction rather than by a check: a shape's open ports are what its links consume, and the fragment algebra refuses a second edge at any port. The nine ADR prototypes live on as tests in both forms — they compile with no explicit type argument anywhere, and they run and resolve exact results. Wired ports, leg order, and re-convergence are asserted edge by edge against the port names the engine's own fixtures use, and every junction graph validates against `LocalStageCatalog`. Branch order is argument order and is identity-bearing: swapping two branches, or two merged sources, produces a different document and a different fingerprint, while two builds of one program produce identical bytes. **Deliberately absent**: no fluent cycle spelling (see Cycles), no graph-builder DSL, and two- and three-input overloads only — wider joins chain, and the chain is honestly two junctions with two fingerprints. **What it costs**: a junction is a local stage, so a graph with one declares `nondeployable` *and* `ephemeral-identity` even when every branch is a registered stage under a name the author chose, and it fails catalog validation at each local seam exactly as any mixed chain has since ADR 0004. A fan-out pipeline built entirely from registered stages is therefore not expressible until a provider can register a junction of its own. |
| Cycles | P2 | M4 | Implemented | Liveness validation requires an explicit buffer/delay boundary and has deadlock tests. The local engine refuses a cycle before anything executes unless it passes a boundary that can answer without room below it — a declared buffer whose overflow policy is not backpressure; a backpressuring buffer of any capacity is refused like an implicit handoff, and the diagnostic names the loop's node path so an author knows where to put one. The rule is "every cycle passes one" rather than "some cycle does", answered by deleting the relieving nodes and asking whether any loop survives, which is the same claim without enumerating cycles. A self-loop is a cycle of one node and gets that test rather than M0's special refusal, which is removed from the definition plane as ADR 0005 ratified. Two shapes a cycle makes reachable are refused by name: a loop nothing outside feeds, and a graph whose every branch runs back into a junction and therefore has no terminal. **Completion is the corrected part, and it corrects this project's own design note.** Closing every external input of a cycle does not end it and must not: the elements circulating inside are a live stream, and for an iterative computation that is the run rather than its tail. A cycle ends from inside, by a stage on the loop that ends its own stream — proved by a feedback graph whose take on the loop ends the run and whose completion walk goes all the way round and back to the segment it started at without recurring forever — or from outside by a stop: cancellation abandons it, and a shutdown cuts every feedback edge, which is "stop pulling" said to the only other place work enters a graph, drains what that channel held, and ends the run successfully. Otherwise it does not end: a loop whose elements all die inside it goes quiet rather than completing, no quiescence detection is claimed, and the hang is documented rather than guessed away. A take on the *exit leg* of the loop's fan-out does not stop the loop and is named as a trap. A paused loop holds its own circulating stream and keeps it: checkpoint 5 pauses a loop carrying one element that counts its own laps and asserts the observed laps are contiguous across the hold, which a run that lost or duplicated the circulating element could not satisfy. No fluent C# spelling, and that is ADR 0006's decision rather than a gap: a fluent cycle would hide the relieving boundary this rule needs an author to see. A loop is authored through the fragment algebra, where edges are explicit, and M4.2 added the operator that was missing there — `GraphFragmentComposer.Wire`, which joins an open output to an open input of one fragment and is what a cycle or a re-convergence needs. ADR 0005's parenthetical that an explicit delay also relieves a cycle is **corrected rather than implemented** since M4.3 wave 1: a delay waits for room below it exactly as a backpressuring buffer does — its window fills and the pump above it then waits for a slot only the pump below could free — so it postpones the deadlock instead of breaking it, and a cycle whose only boundary is a delay is refused like any other waiting loop with the delay named in the path. The predicate stays a declared buffer whose overflow policy is not backpressure, and nothing else. The proofs here remain over documents built directly. |
| Custom stage provider SDK | P1 | M4 | Research | Registered implementation and serialized descriptor compatibility are validated. |

## Flow control and execution

| Capability | Tier | Target | Status | Required semantic proof |
|---|---:|---:|---|---|
| Non-blocking demand/backpressure | P0 | M2 | Implemented | A producer never exceeds downstream credit at every bounded boundary. |
| Bounded buffers by default | P0 | M2 | Implemented | Capacity and memory bounds are testable; no hidden unbounded mailbox is used as flow control. |
| Overflow policies | P1 | M2 | Implemented | Backpressure, drop-oldest, drop-newest, drop-buffer, and fail report distinct outcomes. Inherited by a junction's own boundaries and tested there since M4.1 checkpoint 5, which closes checkpoint 3's inherited-but-untested note: a dropping buffer written immediately below a row-building junction is that junction's output channel, so the policy answers the junction's own offer — the pump keeps building rows while the sink is held rather than being paced by it, and every row is accounted for as delivered or counted as dropped. A failing one faults the run with `BufferOverflowException` raised at that offer. An overflow policy on a balance's leg remains unreachable by construction and is recorded as such rather than tested. |
| Operator fusion | P1 | M2 | Implemented | Compatible adjacent stages share an executor without changing element semantics. |
| Explicit async boundary | P1 | M2 | Research | Placement/concurrency changes are visible; ordering contract remains explicit. |
| Credit protocol across Orleans boundaries | P0 | M3 | Implemented | A call in flight is credit spent and its reply is the grant; nothing on the wire carries credit. Neither an awaited grain call nor a stream publication is counted as downstream demand: each adapter's bound is what admits the next element. |
| Partition-aware placement | P1 | M3 | Research | Partition ownership, rebalance, ordering, and failover are specified. Half of it exists on `main` and the row does not advance on half: placement of run grains and per-key executor grains is a hosting option (cluster default, random, prefer-local, hash-based) and per-key ordering is proven, while ownership, rebalance, and cross-silo keyed evidence are a recorded M3 deferral (see the roadmap) and a single-silo suite cannot show where activations landed. |
| Pause, resume, drain, shutdown, and abort | P1 | M2 | Implemented | Each control has distinct state transitions and in-flight behavior. Proven across branching topologies since M4.1 checkpoint 5, and per junction rather than in general: a pause reaches quiescence on a partition **holding an element it has already routed**, a broadcast that cannot pull because one leg is full, a balance with no willing leg, a concat asleep on the input whose turn it is while another has one ready, a merge asleep on every input, a zip holding a column, a combine-latest remembering every input's latest, and a loop with its own stream circulating — and every one of them resumes with what it held delivered once, unchanged, and in order. The held states are reachable only because a sink probe stops a consumer inside one of the runtime's own waits rather than inside an author's callback, which blocks quiescence by design. The M2 quiescence counters needed no change for junctions — they count segments and callbacks, and a junction is a segment — but the claim they rest on did not hold: a channel sink's write into a full channel reported nothing, so a run holding an element there could never quiesce and `PauseAsync` hung rather than failed. Fixed by the bracket every other wait already had; the hole was never junction-specific and its regression lives with the linear suite. Resume-then-repause storms on a diamond and on a graph mixing partition, merge, broadcast, and zip neither deadlock nor lose, duplicate, or reorder an element. The per-junction memory bounds of ADR 0005 are asserted *through* a pause: one element for a partition (with the sibling leg starving for exactly as long), none for a broadcast or a merge that is waiting rather than placing, N−1 columns for a zip, N for a combine-latest. |
| Kill switch and external shutdown control | P1 | M2 | Implemented | Single-run control is a RunHandle intrinsic (ADR 0004): shutdown drains, disposal cancels; a switch shared across runs is a separate documented contract. The drain-versus-abandon split is proven across branching topologies since M4.1 checkpoint 5, on one graph in one held state so that the two differ by nothing but the request: a diamond holding its first row delivers everything it admitted under shutdown and only the row already inside the author's callback under cancellation, and a graph mixing a partition, a merge, and a declared buffer drains all of it. What "admitted" means is exact rather than estimated, because an emit into a source probe completes when the run has taken the element. Disposal mid-flight is asserted once per junction kind and once for a cycle, and the load-bearing claim is that it *returns* — it waits for every segment to leave its loop, so a pump that could not be woken from its own wait would hang rather than fail — with the outcome cancelled, every enumerator released including the per-lap ones an endless source hands out, and a second disposal changing nothing. |

## Lifecycle and failure

| Capability | Tier | Target | Status | Required semantic proof |
|---|---:|---:|---|---|
| Completion propagation | P0 | M2 | Implemented | Downstream completion and upstream resource release are deterministic. |
| Failure propagation | P0 | M2 | Implemented | Downstream receives failure; upstream receives cancellation unless recovery intercepts it. Proven *sideways* since M4.1 checkpoint 5, which is the statement a graph adds to a chain: a failure on one leg of a fan-out reaches the sibling leg as cancellation and not as an ordinary end, proved by an asynchronous callback on that branch holding the run's own token and recording which of the two it observed. ADR 0005's first shared rule — an input's failure fails the run whether or not that input was being read — was already proven across a fan-in by checkpoint 2. |
| Downstream cancellation | P0 | M2 | Implemented | Early sinks cancel upstream and release resources. |
| Cancellation of async work | P0 | M2 | Implemented | Stage cancellation reaches `Task`, `ValueTask`, and later F# `Async` adapters. |
| Supervision: stop | P1 | M5 | Research | The failing stage fails the defined section or graph. |
| Supervision: resume | P1 | M5 | Research | The failing element is dropped while compatible stage state is retained. |
| Supervision: restart stage | P1 | M5 | Research | The failing element is dropped and declared local stage state resets. |
| Retry element | P1 | M5 | Research | Attempt count, backoff, idempotency, and poison-element handling are explicit. |
| Recover with element or alternate source | P1 | M5 | Research | Completion after fallback and source-switch boundaries are distinct. |
| Restart source/flow/sink section with backoff | P1 | M5 | Research | Reset scope, jitter, restart budget, and in-flight loss window are documented. |
| Durable resume after process/silo failure | P1 | M5 | Research | Checkpoint, source cursor, sink commit, and replay semantics are proven together. |

## Linear operators

| Group | Planned operators | Tier | Target | Status | Contract note |
|---|---|---:|---:|---|---|
| Stateless mapping | map/select, filter/where, choose/collect, map-concat/select-many | P0 | M2 | Implemented | All four are accounted for, and one of them by a decision rather than by code. `Select` and `Where` are members of both `Source<T>` and `Flow<TIn,TOut>` (`Source.cs`, `Flow.cs`) with the LINQ semantics the LINQ names promise — one element in and one out in order, and elements dropped but never reordered — and are exercised throughout `OperatorTests`, `OperatorAuthoringTests`, and effectively every graph in the suite. **`Choose` is deliberately absent from C# and ADR 0005 ratified that**: `Where` composed with `Select` covers the semantics, and every candidate C# spelling — tuple returns, out parameters, sentinel nulls — was worse than the composition it replaced, because the language has no option type to make it honest. The F# frontend gets `choose` over the shared algebra in M7. The row is not silent about it and the question does not reopen per wave. **Map-concat is `SelectMany` and lands in M4.3 wave 2**, which is what this row was waiting for: `Func<T,IEnumerable<TNext>>` flattened in order, one inner sequence read to its end before the next element is asked for, so the result's order is a function of the input alone. It is bounded by construction — the inner sequence is read one element at a time and never collected, a boundary below the stage backpressures the enumeration, the run's token and the pause gate are examined between two inner elements, and the enumerator is released on every path including the one where a stage below ends the stream part way through (`FlatteningTests`, `BatchingCompositionTests`). An empty sequence drops its element, which makes filtering a special case of flattening; a function answering `null` fails the run rather than being read as "nothing". Emitting several elements from one is a new engine seam — `LocalStageOutcome.EmitMany` — and it is the walk an element already takes, entered part way down, rather than a new pump. |
| Async mapping | ordered parallel map, unordered parallel map, sequential async map | P0 | M2 | Implemented | |
| Stateful mapping | stateful map-concat, scan, async scan | P1 | M2 | Implemented | Two of the three are code and the third is a decision, which is what the row was waiting for. **`Scan` exists and has since M2**: `Source<T>.Scan` and `Flow<TIn,TOut>.Scan` emit one state per element and never the seed, an empty stream emits nothing, and the state is per run so a flow carrying one starts from the seed in every graph and every run of each (`OperatorTests`). **Async scan ships in M4.3 wave 3 as `ScanAsync(seed, folder)`** on both types, taking `Func<TState,T,CancellationToken,Task<TState>>`, and every one of the three things wave 2 said had to be proven before it could ship is proven: the state is per run (a flow carrying one starts from the seed in each of two runs), a failure mid-fold leaves the run reporting the author's own exception instance, and a pause parks between two folds, holding the state the last one produced (`AsyncFoldTests`). **What changed is the shape, and wave 2's own sketch is corrected rather than implemented.** That sketch was "the asynchronous stage with a concurrency of one, ordered, with the state threaded by a wrapper"; it would have worked and it was the wrong shape, because one fold can never run beside another — the state the next element folds into is this fold's answer — so a window, an admission rule and a bounded channel in front of them are machinery with nothing to do, and the sequentiality would have rested on the parallel pump's admission rule rather than on the operator's shape. `ScanAsync` is therefore a **fused** stage that awaits on the segment's own thread, and the difference is measurable rather than argued: with a fold held at its first element the source has produced exactly the element being folded, where a boundary-based one would have run a handoff channel ahead. The folder receives the run's own token, one fold runs at a time with the overlap asserted as a peak of one, and a folder that ignores its token delays a stop until it returns — the slow-callback rule, which binds harder here than for `SelectAsync` because a fold is awaited to its outcome rather than abandoned. **Stateful map-concat stays expressible rather than absent** and is named as such: `Scan` into a state that carries what to emit, followed by `SelectMany` over that state, is the composition, and all three halves are implemented and tested — a dedicated operator would be sugar over stages this vocabulary already has, and it is not written until a use shows the composition reading badly. |
| Reduction | fold/aggregate, async fold, reduce | P1 | M2 | Implemented | **Fold exists and is spelled `Aggregate`**, per the naming rules: `Sink.Aggregate(seed, folder)` and the sink-factory form `To(s => s.Aggregate(...), "name", out slot)` are the ordinary terminal of this suite, the document stage id is the semantic `fold`, and the result resolves through a declared slot (`SinkTests`, `RuntimeFixtures.Summing`, most of `ExecutionTests`). **Async fold ships in M4.3 wave 3 as `Sink.AggregateAsync(seed, folder)`**, with the sink-factory spelling `To(s => s.AggregateAsync(...), "name", out slot)` beside it, and it closes the gap wave 2 named exactly: an asynchronous segment's terminal is its callback and produces no result, so `ForEachAsync` declares none, and this is the result-bearing asynchronous terminal that was missing. It is a terminal that awaits rather than a second asynchronous segment, for the reason `ScanAsync` is a fused stage — one fold runs at a time because the next one folds this one's answer, asserted as a peak overlap of one — so it declares no concurrency bound at all, which is the whole of what separates it from `ForEachAsync`. The result resolves through the ordinary slot machinery when the run ends, faults with the run's failure, cancels with its cancellation, and a shutdown resolves the state folded so far (`AsyncFoldTests`). The composition wave 2 recorded — `SelectAsync(MaxConcurrency = 1)` into `Last()` — remains honest and remains not the same thing, because it makes every intermediate state an element. **Reduce is still missing, and it is missing in spelling rather than in capability.** It is a fold whose seed is the first element, resolving the combination of every element and failing on an empty stream; today it is written as an `Aggregate` over a state that carries "nothing yet", which is exact for a reference type and awkward for a value one. A first-class spelling needs a terminal that takes its seed from the stream rather than from the author, which is a new answer to "what did this sink start from" and not a new argument to an existing one, so it is named here rather than folded in beside two operators whose contracts this wave was proving. |
| Slicing | skip/drop, take, skip-while, take-while, take-through | P1 | M2 | Implemented | |
| Batching | grouped, sliding, grouped-within, weighted grouped-within | P1 | M4 | Implemented | All four ship in M4.3 wave 2, on both `Source<T>` and `Flow<TIn,TOut>`, emitting `IReadOnlyList<T>` copied out per group so a group an author keeps is theirs. **Every batch emits its last partial group when its stream ends and never an empty one**, which is the engine seam this row needed: a stage is asked what it is still holding when its segment's loop ends without being cancelled, and the answer travels through the stages below the one that gave it exactly as an element would. That makes a group an ordinary element to everything downstream — a spent `Take` refuses one offered after its bound, and a boundary a downstream stop closed abandons one — so the answer is independent of fusion, proved by asserting `Take(5).Grouped(3)` and `Grouped(3).Take(1)` and the same graph split across a declared buffer (`BatchingTests`, `BatchingCompositionTests`). A cancellation abandons the open group; a shutdown delivers it, because a shutdown ends the stream as running out would. `Grouped(n)` holds at most `n` elements and that is its whole bound. `Sliding(n, step)` is three operators under one name — overlap below the size, partition at it, sample above it, with the skipped elements counted past rather than buffered — and its end-of-stream rule is one sentence that covers both familiar cases: **the buffer leaves as a final window only if it holds an element no window has carried**, so a stream shorter than the window emits everything it had and a stream that ended mid-overlap emits nothing new. `GroupedWithin(n, window)` closes on size **or** time, whichever comes first, and **the window belongs to the group rather than to the stage**: it starts when the group's first element arrives and is gone when the group leaves, which makes "an empty window emits nothing" a consequence rather than a special case — asserted by advancing a controlled clock ten windows' worth over a quiet stream and then timing the next group from its own first element (`GroupedWithinTests`). The boundary is one tick either side. The weighted form takes a cost function and **closes the group before the element that would break the bound**, so the bound is never exceeded and that element starts the next group, from whose arrival the next window is timed; a negative weight and a weight no group could ever carry both fail the run, as they do for a throttle by cost. **What a clock-closed batch costs is a boundary, and it is stated rather than hidden**: `GroupedWithin` runs as its own segment with one bounded handoff in front of it, because only a segment waiting on its own input channel can be woken while nothing is arriving, and emitting on silence is the whole reason to write it instead of `Grouped`. The timer never touches an element — it signals the very wakeup latch an asynchronous segment sleeps on, and the one thread that owns the stage builds, closes, and hands over every group — so nothing here needs a lock. The difference from a fused batch is measured: a run of `Grouped` pulls its source exactly as far as the open group, a run of `GroupedWithin` runs ahead by its handoff. Every wait takes the checkpoint-5 bracket: a paused run comes to rest inside one with the clock still, a window that closes during a pause delivers on resume rather than under the pause, a shutdown releases it with the group delivered, and a cancellation abandons it with disposal returning. Composition across junctions is measured rather than argued this time — a batch per leg of a broadcast, a batch feeding a merge, a timed batch on one leg woken by its own window, and two batches in one chain. |
| Timing | delay, initial delay, take-within, skip-within, timeout, valve | P1 | M4 | Implemented | The clock is the host's `TimeProvider`, resolved at materialization and carried by the run (ADR 0005): no stage reads `TimeProvider.System`, the document carries every duration as ticks and never a clock, and a controlled clock in `Orleans.Dataflow.Testing` is what makes every claim below an exact one rather than a hope about scheduling. `Delay` shifts rather than paces — each element starts its own wait when the stage takes it and results are emitted in input order, so a burst arriving 400ms apart leaves 400ms apart and a whole delay later; the required holdback is how many wait at once, one more sits in the handoff in front of them, and the declared overflow policy answers the next arrival (proved as how far a recording source got: four pulls for a holdback of two, and no fifth). `InitialDelay` holds the first element until the duration has passed since the run started and nothing after it, and does not delay a stream whose first element is later than that. `SkipWithin` drops what arrives inside its window and never waits, with the boundary asserted one tick either side. `TakeWithin` keeps what arrived before its deadline, refuses the element at or after it, and ends its own stream from a timer when nothing arrives at all — with the honest limit that a source asleep in one of this runtime's own waits learns at its next element, so a ticking run ends within one interval of the deadline rather than at it. `Timeout` fails the run with `StreamTimeoutException` when the gap between two elements, or between the run's start and the first, exceeds the declared one; its watchdog re-arms rather than firing on a stream that kept its promise. Every wait takes the pause bracket: a paused run comes to rest inside a timing wait without the clock moving, a wait that finishes during a pause parks instead of delivering, a shutdown releases it and keeps the element, and a cancellation abandons it (disposal returns, which is the claim that would hang). The one exception is `Delay`, whose elements are in an asynchronous window: a pause waits them out and a shutdown drains them, exactly as both do for an author's callback in flight, bounded by the delay. Time passes for a paused run, so a run held past a timeout's gap fails — stated and tested rather than discovered. **The valve is the one operator here that reads no clock**, and it is the first control this vocabulary declares in the middle of a chain rather than at one of its ends: `Valve(controlName, initialMode)` declares an `IValve` on the node's own control port, resolved by name from the run handle as soon as the run exists. Nothing in the control machinery needed a line for that — the graph builder already collected a control from any occurrence, and the planner sorts controls by the port they are declared on rather than by where the node stands — which is what the M2 control seam stretching cleanly turned out to mean. A closed valve holds the element in the segment's hand and backpressures everything above it, with no capacity of its own: what accumulates is exactly the declared buffer above it plus the element the valve holds plus the one in the source's hand, and nothing is dropped. Closing takes effect at the next element and never retroactively; two valves in one chain are two controls and both have to be open; two runs of one graph have two valves. The wait carries the same bracket every wait here carries, so a run held at a closed valve reaches quiescence under a pause, is released by a shutdown with the element delivered, and is abandoned by a cancellation with disposal returning. The state a valve *starts* in is in the document — a graph whose valve starts closed produces nothing until something opens it — and what an author does to it afterwards is never durable topology. |
| Rate | throttle by element/cost, shaping versus enforcing mode | P1 | M4 | Implemented | A token bucket counted in exact integers rather than in tokens per second: budget is held in element-ticks, so the refill is continuous and two per second admits one every half second instead of two at each second's edge (asserted as the moment of emission, not as a count). The bucket starts full — a stream at or below the declared rate is not paced at all — is capped at `MaximumBurst` (defaulting to the rate and written into the document either way, so an idle stream banks one period's worth and not five), and charges what the cost function answers when there is one: four units per second admits one element of cost four per second and an element of cost one a quarter of a second later. `Shaping` waits for budget on the segment's own thread, which backpressures upstream and reports itself to the pause gate; `Enforcing` fails the run with `RateLimitExceededException` on the first element it has no budget for, naming the rate that was broken. Nothing is ever dropped by either mode. Two conditions fail both: an element costing more than the whole burst, which no amount of waiting could admit, and a negative cost, which would give a stream budget back. A cost of zero is a real cost and is not paced. |
| Observation | tap/also-to, termination watch, monitor, completion callback | P1 | M4 | Research | Half of it exists on `main` and the row does not advance on half. **Tap is `AlsoTo` and shipped in M4.2** — broadcast sugar with the main line on the junction's first leg and the branch on its second, so every element reaches both and a branch that stops consuming holds the main line up; a tap is not a fire-and-forget side effect and the row says so. M4.3 wave 2 adds `DivertTo`, its partition-shaped sibling, under Sequence edits. **A completion callback needs no operator and none is added**: `RunHandle.Completion` is the run's own task and reports exactly how the run ended — success, the author's own exception unwrapped and instance-identical, or cancellation — with the run's resources released and its slots settled before it transitions. A `Sink.OnComplete` beside it would be a second spelling of one fact. **Termination watch is deferred with its design tension recorded rather than guessed at.** It wants to report *how* a stream ended as a value, and ADR 0002's slot model is what makes that awkward: a result slot resolves at the end of a run and carries the run's outcome, so a slot typed "how it ended" would fault when the run failed instead of resolving to "failed". The honest shape is therefore a control — resolved when the run starts, carrying a task the author awaits — and the contract that control would have to state is the part that needs measuring rather than asserting: a failure anywhere cancels the run's token, so a stage above the failure observes cancellation rather than that failure, and the run's own `Completion` is where the failure is. Publishing that before proving it would fix a shape by accident. **Monitor is deferred to where it already belongs**: the Testing and observability section's "Stage/run monitor snapshots" row targets M5, `RunHandle.DroppedElements` is already internal and already records that a monitor is what an author will read it through, and a second, weaker snapshot shape invented here would settle that design sideways. |
| Flattening | concat-map, merge-map with bounded parallelism | P1 | M4 | Implemented | Both halves now exist and the row advances on both. **Concat-map ships in M4.3 wave 2 as `SelectMany`** on both `Source<T>` and `Flow<TIn,TOut>`, taking `Func<T,IEnumerable<TNext>>`: one inner sequence read to its end before the next element is asked for, so the result's order is a function of the input alone. It is bounded by construction rather than by a declared number — the run owns the enumerator, advances it one element at a time, pushes each element through the stages below, examines the run's token and the pause gate between two inner elements exactly as the source pump does between two pulls, and releases the enumerator on every path including the one where something below ends the stream part way through (`FlatteningTests`). **Merge-map ships in M4.3 wave 3 as `MergeMap(options, selector)`**, taking `Func<T,IAsyncEnumerable<TNext>>` and, over the same machinery and the same document node, `Func<T,IEnumerable<TNext>>`. One sentence is its order contract and both halves of it are asserted: **emission is unordered across inner sequences, and the order of each inner sequence is preserved.** An element is emitted as soon as the sequence it came from produces it, whichever sequence that is — proven with one inner sequence gated and another free, whose three elements are all delivered before the held one's first, an ordering no concat-map could produce — and an inner sequence is never asked for its next element until the one before it has been delivered, which is what makes its own order survive the interleaving and is also the whole of the operator's memory bound. `MaxConcurrency` counts **open enumerations** and a slot is freed when one **ends** rather than when it produces, so an empty inner sequence frees its slot at once and an endless one holds its slot for as long as the run does; the bound is read as how far a held source got — four elements absorbed by a merge-map of two, seven with a declared buffer of four in front, because a buffer written there is the pump's own input channel. It is a new pump and the wave-2 estimate of what one would cost held: a window of enumerations, a slot freed by an ending, and a `Task.WaitAny` over one outstanding `MoveNextAsync` per open sequence plus the arrival of an element. Three things that estimate did not say are decisions rather than details — downstream room is waited for in the ordinary `Offer` rather than in the wait-set, so an element with no room below parks the one pump instead of a thread per inner; an outstanding step is counted as **a callback in flight** rather than as an idle segment, correcting wave 2's forward guess, because an author's iterator running is exactly what quiescence says is not happening; and each step is observed the moment it completes, from whatever thread completed it, because a pump parked in a full boundary's offer would otherwise never learn that a sibling sequence had failed and would wait for room that is not coming. Every terminal path is proven: a failing inner or selector faults the run and releases the others with `DisposeAsync` awaited to its return, a stream ended below releases the open sequences rather than draining them (an enumeration is not work in flight to be polite to), a shutdown plays the sequences already open out to their natural end, a cancellation abandons and releases them, and a disposal mid-flight returns with both sequences asleep in a step only the run's token could end (`MergeMapTests`). **A graph-valued flatten is still out of scope and the row's words do not promise one**: `MergeMap` flattens `n` local sub-enumerations on one segment's thread, and a source of sources — each inner stream a graph with its own stages, boundaries, and junctions, materialized and torn down per element — is a different feature this engine has no shape for. |
| Deduplication | distinct, deduplicate with explicit bounded state policy | P2 | M4 | Implemented | Both spellings exist and the policy is explicit in both directions. **`Distinct(DistinctOptions)` has required a bound since M2 and gains a declared answer for reaching it in M4.3 wave 2.** `KeyOverflowPolicy.Fail` is the default and keeps the operator's promise exactly — everything emitted was the first of its key, and a bound sized on a wrong assumption reports that with `TrackedKeyOverflowException` instead of quietly becoming a weaker operator. `KeyOverflowPolicy.EvictOldest` is the deliberate weakening and what it costs is asserted rather than described: an element whose key was evicted is emitted a second time if it arrives again, so the stream is distinct over a window of the last `MaxTrackedKeys` keys and **not** over its history (`DeduplicationTests.AnEvictedKeyIsEmittedASecondTimeIfItArrivesAgain`). Age is when a key was first remembered rather than when it was last seen, so a repeat does not refresh a key — also asserted, because an implementation that refreshed would pass every other test here. Ten thousand distinct keys run through a bound of four without faulting. The policy is in the payload under `local-distinct-parameters` beside the bound, because the same stream through the same bound either faults or emits an element twice: two graphs differing only in it are two graphs with two fingerprints. A separate enumeration from `OverflowPolicy` and deliberately so — three of a buffer's five values have no reading here at all. **`DeduplicateConsecutive()` is the bounded one that needs no bound**, because its bound is one element and is a fact about the shape rather than a number an author chose: it collapses runs and never compares across them, so `a a b b a` becomes `a b a`. It uses the element type's own equality, emits its first element because it is the first rather than because it differs from a remembered default, and remembers nothing across runs. Both operators' keys are per run, proved by materializing one graph twice. |
| Sequence edits | prepend, append, divert-to side channel | P2 | M4 | Implemented | All three ship in M4.3 wave 2 and **none of them adds a stage to the vocabulary**, which is the honest thing to say about them and is asserted rather than asserted-about: `a.Append(b)` and `a.Concat(b)` build documents with the same fingerprint, `a.Prepend(b)` is the same junction with its inputs swapped — the head wired to `in-0` and the receiver to `in-1`, which is what "before" means when argument order is identity-bearing — and `DivertTo(predicate, branch)` is a two-legged partition with the main line on `out-0` and the branch on `out-1`, the shape `AlsoTo` gives a broadcast (`SequenceEditTests`). The `params` forms are `Source.From` composed in, and an empty one still builds the junction, because a graph's shape is what the author wrote. Each therefore inherits its junction's contract whole, **including the parts that cost something**: a concat's later input is running and parked in its own bounded channel while the earlier one plays out, and a partition holds one element and waits for the leg it belongs on, so a slow diverted branch holds the main line up for exactly that long and a branch whose stream has ended has its elements abandoned rather than failing the run. A diverted branch may declare its own result, which is carried until the graph is closed and declared beside the main line's. **They are on `Source<T>` only**, and that is a boundary rather than an omission: a junction joins two streams and a `Flow<TIn,TOut>` is a chain with one open input, so there is nowhere for the second stream to enter — the same reason no junction is a flow member. |

C# names should follow .NET expectations where possible. If the Akka.NET behavior differs from LINQ, Orleans.Dataflow uses an unambiguous additional name rather than silently surprising C# callers. For example, `TakeWhile` should follow the ordinary exclusive predicate boundary, while an inclusive variant can be named `TakeThrough`.

| Merge | P1 | M4 | Implemented | No global cross-input order unless a specialized merge supplies one. The local engine's fan-in pump rotates among the inputs that have an element, so a producer that is merely faster cannot starve an element that has already arrived at another input; every element of every input is emitted, each input's own order is preserved, the junction completes only when every input has, it holds one element outside its declared buffers (proved as a peak measured over the whole run rather than sampled), and a failure on any input fails the run including while the pump is asleep on the others. | Concat | P1 | M4 | Implemented | Later input is not consumed as the active input until the prior one completes, except bounded prefetch if declared. "Not consumed" is honest as backpressure rather than as laziness: a run starts every segment, so a later input's source is running and parks in that input's own bounded channel — one element in the channel and one in the source's hand, widened only by a declared buffer — and a downstream completion releases the inputs whose turn never came. | Zip/zip-with | P1 | M4 | Implemented | Positional pairing and early-completion behavior are deterministic. It holds N−1 elements outside its declared buffers (the columns awaiting the slowest one, proved as a peak over the whole run), completes as soon as any input it still needs has ended, discards the partial row at that moment (proved against the combiner's own record, not inferred from the sink), and closes every input it reads so the legs that were still live are released. A failure on any input fails the run including while the pump is asleep on the others, and the combiner's own exception is the run's, unwrapped. A broadcast can feed a zip with no buffer between them: one element per leg per element is exactly one per input per row, which is the head-of-line hazard's benign cousin. | Broadcast | P1 | M4 | Implemented | Every output receives each element; one slow output backpressures by default. The local engine's junction asks every live leg for room before it pulls, so the slow leg paces the stream (proved by how far a held source gets), holds one element outside its declared buffers, drops a leg whose downstream completed, and completes upstream when the last leg leaves. Authored in C# since M4.2 (ADR 0006): `source.BroadcastTo(branches)`, and `source.AlsoTo(branch)` for the tap. The authored document is asserted edge by edge against these very port names in `JunctionAuthoringTests`, and run for its results in `FluentJunctionTests`/`FluentJunctionValueTests`; the proofs in this row remain over documents built directly, which is what they are proofs of. |
| Balance | P1 | M4 | Implemented | Exactly one available output receives each element; fairness is specified. The local engine rotates among the outputs that have room, so a leg with no room is routed around rather than blocking the others, every element arrives exactly once, and one element is held outside the declared buffers. An overflow policy on a balance's leg is unreachable by construction and is recorded as such. Authored in C# since M4.2 (ADR 0006): `source.BalanceTo(branches)`. The authored document is asserted edge by edge against these very port names in `JunctionAuthoringTests`, and run for its results in `FluentJunctionTests`/`FluentJunctionValueTests`; the proofs in this row remain over documents built directly, which is what they are proofs of. |
| Partition | P1 | M4 | Implemented | Routing function and invalid partition behavior are explicit. The local engine's routed junction is the one pump that reads before it waits, because the room it needs is room on the leg its element belongs on and that is what the author's function answers: it reads one element, calls the function exactly once (proved by counting the calls against the elements), holds that element, and waits for its target alone. Head-of-line blocking one element deep is therefore the contract rather than a defect — a leg whose elements are queued upstream starves for exactly as long as the held one waits, proved by how far a held source gets and by the other leg receiving nothing — and it holds one element outside its declared buffers. An answer outside the wired range fails the run, naming both the answer and the arity, because how many legs an occurrence has is stated by its edges and by nothing the function can see. An answer naming a leg whose stream has *ended* does **not** fail the run: that element is abandoned, the junction goes on feeding the legs that remain, and it completes upstream when the last of them leaves. Failing instead was implemented first and measured wrong — a completion walking upstream closes legs while elements are still travelling to them, so the same graph ended successfully or in failure by a race — and abandonment is what this engine already does everywhere for an element arriving at a channel a downstream completion closed; it is not counted as a drop for the same reason. An eager-cancel mode is a declared variant if one is ever wanted, per ADR 0005's escape-hatch pattern. The routed leg's own overflow policy is reachable, unlike a balance's. A partition composes as the canonical split by key into distinct sinks, as legs rejoined through a merge, and as the exit of a feedback loop. Authored in C# since M4.2 (ADR 0006): `source.PartitionTo(router, branches)`. The authored document is asserted edge by edge against these very port names in `JunctionAuthoringTests`, and run for its results in `FluentJunctionTests`/`FluentJunctionValueTests`; the proofs in this row remain over documents built directly, which is what they are proofs of. |
| Unzip/unzip-with | P1 | M4 | Implemented | Output backpressure interaction is explicit: both outputs must have room before the row is pulled, so the two legs advance in lockstep and re-zip without skew (proved end to end since checkpoint 3: a row is split into halves, each half is transformed on its own, and a zip pairs them back positionally with no skew and no buffer between the two junctions). Authored in C# since M4.2 (ADR 0006): `source.UnzipTo(left, right)`, on a source of pairs. The authored document is asserted edge by edge against these very port names in `JunctionAuthoringTests`, and run for its results in `FluentJunctionTests`/`FluentJunctionValueTests`; the proofs in this row remain over documents built directly, which is what they are proofs of. |
| Interleave | P2 | M4 | Implemented | Segment size, fairness, and per-input completion behavior are explicit. The segment size is document payload validated as a positive integer by the reader the runtime itself uses; the rotation is fixed and waits for the input whose turn it is even when another has an element ready, so the emitted sequence is a function of the inputs and the segment size rather than of the scheduler; a completed input leaves the rotation and the remainder continues in order; the junction completes when every input has and holds one element outside its declared buffers. | Combine latest | P2 | M4 | Implemented | Initial completeness, which-input-emits, and completion rules are deterministic. | Tick/clock source | P1 | M2 | Implemented | Slow-consumer behavior and missed ticks are explicit. `Source.Tick(initialDelay, interval)` emits the tick's number as a `long`, and the number is the contract: tick `n` is due at `initialDelay + n * interval` after the run started whether or not it was emitted, so a consumer that was busy for three intervals receives a number three higher and can see that it fell behind. A tick that comes due while the run is busy is skipped and not queued — a queue of moments that have already passed grows without bound whenever the consumer is slower than the interval — which is the reminder trigger's missed-tick honesty applied to a pull-paced source, and it is asserted with a consumer held inside a gate for four intervals (`0, 1, 5`) rather than inferred. Akka emits a fixed element instead, which is honest for a source that never skips; a stream of a constant here is one `Select` away. Endless, non-durable, and run-scoped the way the .NET timer adapter is activation-scoped: two runs of one graph tick independently from their own zero, the source is bounded by whatever is written below it, its wait reports itself to the pause gate, a shutdown ends it as running out would, and a cancellation abandons it. |
