# Capability matrix

This document is the working definition of logical parity for Orleans.Dataflow. It tracks capabilities and semantics, not API spelling or implementation similarity.

Akka.NET Streams is the reference for the general streaming model. Microsoft Orleans and .NET documentation define the constraints of Orleans-native adapters. An item is not complete merely because a method with a similar name exists.

## Status vocabulary

- **Research**: semantics are understood and linked, but no contract is approved.
- **Specified**: public and runtime semantics are documented and reviewed.
- **Implemented**: code and focused tests exist.
- **Qualified**: contract, failure, and integration tests prove the documented behavior.
- **Deferred**: intentionally outside the current milestone, with a recorded reason.

Every row starts at **Research** and advances only together with its evidence; Implemented rows have code and focused tests on `main`.

## Capability tiers

- **P0**: required to call the result a bounded dataflow runtime at all.
- **P1**: required for the C# logical-parity gate.
- **P2**: expected before or shortly after 1.0, depending on evidence and package boundaries.

## Graph and materialization

| Capability | Tier | Target | Status | Required semantic proof |
|---|---:|---:|---|---|
| Immutable typed source, flow, and sink blueprints | P0 | M0 | Implemented | Composition does not execute work; instances are thread-safe and reusable. |
| Reusable `Flow<TIn,TOut>` composition | P0 | M0 | Implemented | Reusing one fragment creates independent node identities and runtime state. |
| Closed runnable graphs | P0 | M0 | Implemented | Validation can distinguish open ports from a materializable graph. |
| Named graph, stage, port, and revision identity | P0 | M0 | Implemented | Deterministic serialization, collision checks, and compatible revision rules. |
| Runtime materialization | P0 | M2 | Implemented | Each run allocates independent runtime resources and exposes completion. The document and the binding table are required to describe the same node since M4.1 checkpoint 5, which closes checkpoint 2's recorded gap: the stage a node declares is compared with the stage its binding's kind declares, so a `merge` bound to a zip, a `select` bound to a where, or a `first` bound to a last is refused instead of executing the binding while the fingerprint goes on describing the document. The check is asked **last**, after every structural refusal — a node fed by two streams that is not a fan-in, a junction wired at a port its stage does not declare, a shape that cannot stand where the document puts it — because those name what the runtime actually cannot do and are sharper; what reaches the new check is the residue nothing structural could separate. It is unreachable through the authoring API, which builds the node from the binding's own kind. |
| Typed result slots | P1 | M2 | Implemented | Source, flow, sink, and lifecycle results are declared as typed named slots and resolved per run without persisting runtime objects; a run rejects slots from another graph identity, revision, or import scope. **A result that crosses a grain boundary is bounded since M4.5**, which closes the `Collect`-over-a-cluster foot-gun ORLEANS-RUNTIME.md's open question 2 named: a silo declares a cap in bytes with `LimitResultSize`, defaulting to one mebibyte, and a value past it fails *that slot* with `ResultTooLargeException` carrying the slot, the measured size, and the bound. The size is exact — the value is serialized through a writer that counts and discards, so an oversized result is refused without ever being materialized as bytes or sent — and the enforcement point is the grain building the envelope, so the run itself stays `Completed`, its completion stays successful, and its other slots resolve normally. Not a codec error, not a faulted run, not a poll that never answers. The bound is a silo's rather than a document's, so two silos may accept one pipeline and disagree about what it may return; that is stated rather than hidden, and it is the same deployment-scoped honesty the binding registry carries. |
| Named multiple results | P1 | M4 | Implemented | Results remain type-safe and versionable across distributed execution. Since M4.2 a graph declares one result per result-bearing branch: the branch names its own slot where its sink is written, the document declares that name against the branch's own terminal, and one run resolves every one of them independently (`JunctionAuthoringTests`, `FluentJunctionTests`). Two branches under one name are refused by the document's own uniqueness rule, which this surface reaches for the first time — a linear graph is closed by one `To` carrying at most one name. The typing is the C# compiler's, as it is for every local graph: a slot carries `TResult` from the sink that declared it. A branch's slot is the one slot that exists before its graph does, because a branch is written as an argument of the junction call that consumes it; it names its graph from that call onwards, reading it earlier throws rather than answering with a fingerprint of nothing, and a branch that declares a result closes exactly one graph instead of repointing the first graph's slot. ~~The distributed half is not proven and cannot be yet~~ **The distributed half is proven since M4.5**, and by the change that made it possible rather than by a new result mechanism: a registered junction is not a local stage, so a branching document declares no token, `AsPipeline` accepts it, and a cluster runs it. `ResultSizeTests.ADeployableBranchingPipelineResolvesBothOfItsResults` materializes one such pipeline through the remote handle and resolves both slots independently; the same shape with one oversized leg is what the result-size cap is measured on. What is still not proven is a multi-result run under placement or failover: these are single-silo tests. |
| Explicit fan-in/fan-out graph construction | P1 | M4 | Implemented | All ports are connected exactly once unless a junction contract states otherwise. The M4.2 authoring surface (ADR 0006) spells every junction the M4.1 engine runs: `BroadcastTo`, `BalanceTo`, `PartitionTo`, `UnzipTo`, and `AlsoTo` take branches and close the graph the way `To` closes a chain; `Merge`, `Concat`, `Interleave`, `Zip`, and `CombineLatest` join sources and return one; `Fork`/`ForkMerge` carry the diamond a tree cannot express. A port is connected exactly once by construction rather than by a check: a shape's open ports are what its links consume, and the fragment algebra refuses a second edge at any port. The nine ADR prototypes live on as tests in both forms — they compile with no explicit type argument anywhere, and they run and resolve exact results. Wired ports, leg order, and re-convergence are asserted edge by edge against the port names the engine's own fixtures use, and every junction graph validates against `LocalStageCatalog`. Branch order is argument order and is identity-bearing: swapping two branches, or two merged sources, produces a different document and a different fingerprint, while two builds of one program produce identical bytes. **Deliberately absent**: no fluent cycle spelling (see Cycles), no graph-builder DSL, and two- and three-input overloads only — wider joins chain, and the chain is honestly two junctions with two fingerprints. **What a *local* junction costs**: it is a local stage, so a graph with one declares `nondeployable` *and* `ephemeral-identity` even when every branch is a registered stage under a name the author chose, and it fails catalog validation at each local seam exactly as any mixed chain has since ADR 0004. **A junction of a provider's own costs none of it, since M4.5**: `RegisteredStage.FanOut`/`FanIn` produce typed handles over a registered multi-port stage, `source.FanOutTo(junction, name, payload, branches)` and `a.FanIn(junction, name, payload, b)` attach them through the very `Split`/`Combine` machinery the local spellings use, and the closed document declares no capability token at all — every occurrence is registered, every one is named, every port carries the provider's own contract, and `AsPipeline` accepts it. The M4.2 test asserting a local junction costs both tokens now has a sibling asserting their absence on the same shape. Arity and port order are the specification's: a call supplies one branch per declared output port, in the catalog's canonical port order, and a call with the wrong number is refused naming both numbers. The mixing rule is unchanged — a lambda branch under a registered junction is still one `element-contract-mismatch`, because a local port still declares the opaque contract. |
| Cycles | P2 | M4 | Implemented | Liveness validation requires an explicit buffer/delay boundary and has deadlock tests. The local engine refuses a cycle before anything executes unless it passes a boundary that can answer without room below it — a declared buffer whose overflow policy is not backpressure; a backpressuring buffer of any capacity is refused like an implicit handoff, and the diagnostic names the loop's node path so an author knows where to put one. The rule is "every cycle passes one" rather than "some cycle does", answered by deleting the relieving nodes and asking whether any loop survives, which is the same claim without enumerating cycles. A self-loop is a cycle of one node and gets that test rather than M0's special refusal, which is removed from the definition plane as ADR 0005 ratified. Two shapes a cycle makes reachable are refused by name: a loop nothing outside feeds, and a graph whose every branch runs back into a junction and therefore has no terminal. **Completion is the corrected part, and it corrects this project's own design note.** Closing every external input of a cycle does not end it and must not: the elements circulating inside are a live stream, and for an iterative computation that is the run rather than its tail. A cycle ends from inside, by a stage on the loop that ends its own stream — proved by a feedback graph whose take on the loop ends the run and whose completion walk goes all the way round and back to the segment it started at without recurring forever — or from outside by a stop: cancellation abandons it, and a shutdown cuts every feedback edge, which is "stop pulling" said to the only other place work enters a graph, drains what that channel held, and ends the run successfully. Otherwise it does not end: a loop whose elements all die inside it goes quiet rather than completing, no quiescence detection is claimed, and the hang is documented rather than guessed away. A take on the *exit leg* of the loop's fan-out does not stop the loop and is named as a trap. A paused loop holds its own circulating stream and keeps it: checkpoint 5 pauses a loop carrying one element that counts its own laps and asserts the observed laps are contiguous across the hold, which a run that lost or duplicated the circulating element could not satisfy. No fluent C# spelling, and that is ADR 0006's decision rather than a gap: a fluent cycle would hide the relieving boundary this rule needs an author to see. A loop is authored through the fragment algebra, where edges are explicit, and M4.2 added the operator that was missing there — `GraphFragmentComposer.Wire`, which joins an open output to an open input of one fragment and is what a cycle or a re-convergence needs. ADR 0005's parenthetical that an explicit delay also relieves a cycle is **corrected rather than implemented** since M4.3 wave 1: a delay waits for room below it exactly as a backpressuring buffer does — its window fills and the pump above it then waits for a slot only the pump below could free — so it postpones the deadlock instead of breaking it, and a cycle whose only boundary is a delay is refused like any other waiting loop with the delay named in the path. The predicate stays a declared buffer whose overflow policy is not backpressure, and nothing else. The proofs here remain over documents built directly. |
| Custom stage provider SDK | P1 | M4 | Implemented | Registered implementation and serialized descriptor compatibility are validated. **The executable half ships in M4.5 and the row advances on that half**: a provider registers a catalog and one `IDataflowStageFactory` per `ProviderId`, and the factory answers with a `DataflowStageRuntime` in one of the shapes the engine runs — four linear (source, fused element, asynchronous element, terminal) and, new in M4.5, nine junctions (`Broadcast`, `Balance`, `Partition`, `Unzip`, `Merge`, `Concat`, `Interleave`, `Zip`, `CombineLatest`). **One seam, two hosts, and that is the load-bearing change**: the mirror the Orleans package published for silos in M3 moved into the core package under the same names, so `LocalDataflowHost(builder => builder.AddCatalog(...).AddFactory(...))` and `AddOrleansDataflow(...)` take the very same factory value and unwrap it through one internal adapter. A provider writes its vocabulary once and it runs in either runtime, which is checked rather than asserted: a fully registered branching pipeline materializes and runs on the in-process host through public API only, and the same shape runs in a cluster. A factory is asked **once per node per materialization** — asserted by counting, because a junction is asked about twice while a plan is built and a planner that did not remember the answer would build two runtimes with two lots of per-run state — and asked again for a second run, so whatever a provider's closures hold is that run's own. **What a factory is told is deliberately narrow**: the node as the document declares it and the specification it resolved to, and nothing else. In particular a junction's ports come from the specification rather than from the factory, so a provider cannot disagree with its own catalog entry about its own shape. **The usability half ships in M4.5b, and the row stays at Implemented on it rather than advancing.** Two things, and both are patterns rather than frameworks. **A conformance kit**: `Orleans.Dataflow.Testing.ProviderConformance` takes a provider's own catalog, its factory, and one accepted payload per stage, and answers nine checks that were previously nine hand-written tests per provider — ports declare real contracts in the canonical order three places read; every payload has a reader, and that reader refuses an added member, a removed required member, a retyped member, and a payload that is not an object, naming the member in single quotes each time, while accepting a removed *optional* one; a catalog fingerprint is a function of the registration and not of its order or of which read produced it; the factory answers for every stage its catalog declares and refuses a stranger — an unknown identifier and an unregistered major version alike — by throwing and naming it rather than by a null reference, an index, a missing key, or a cast; the runtime it builds has the shape the specification's ports imply, with a terminal producing a result exactly when its stage declares a result port and an unzip's projections matching its leg count; the typed handle the specification implies is creatable and one of another shape is refused; no payload string resolves to a CLR type or carries an assembly-qualified name; and no public `*Options` type of the core packages names anything of the provider's — which is this milestone's "provider packages do not leak their configuration into core option types" made mechanical. The mutations are generated from the sample rather than described, so a payload that grows a member grows its checks with it, and the kit **refuses to measure nothing**: a catalog with no stage of the named provider, a declared stage with no sample, and a sample naming an undeclared stage are all refused at construction. **Both shipped vocabularies are its first consumers and both pass**: the .NET adapters in the core suite, the Orleans adapters inside the cluster collection, because building a stream stage resolves a stream provider and building a reminder trigger reads the cluster's own minimum period. It found one real gap in doing so — `DotnetStageFactory` implemented the engine's *internal* factory interface rather than the public seam this milestone published, so the SDK's own vocabulary could not be run through the SDK's own kit; it now implements `IDataflowStageFactory` and is unwrapped through the same adapter the Orleans factory already used. And the kit is checked as an instrument before anything is asserted through it: each check is pointed at a provider broken in the one way that check is about, with a correct control that passes all nine. **Typed parameter builders**: the pattern is named and documented rather than invented, because both real providers had already grown it — a payload lives in three places (the member names and one `TryRead`, one `public static CanonicalJsonValue XxxParameters(…)` per stage, and a validator over the reader), the factory reads through the same `TryRead`, and the writers emit the very bytes the raw payloads had, so adopting them changes no document and no fingerprint. A generic builder framework was considered and rejected: it would buy deriving the reader from the writer at the price of a second way to spell a payload and a shape fixed before three providers exist. **What is still not here, and why the status does not move**: typed element wrappers and per-stage registration. A provider still casts `object` at the element boundary; the kit builds runtimes without ever running one, so a source that throws on its first pull passes every check; and no provider outside this repository has used any of it, which is the evidence a Qualified reading of "the SDK works for its users" would need. Serialized descriptor compatibility is the catalog fingerprint and the golden catalog tests, which predate this row. |

## Flow control and execution

| Capability | Tier | Target | Status | Required semantic proof |
|---|---:|---:|---|---|
| Non-blocking demand/backpressure | P0 | M2 | Implemented | A producer never exceeds downstream credit at every bounded boundary. |
| Bounded buffers by default | P0 | M2 | Implemented | Capacity and memory bounds are testable; no hidden unbounded mailbox is used as flow control. |
| Overflow policies | P1 | M2 | Implemented | Backpressure, drop-oldest, drop-newest, drop-buffer, and fail report distinct outcomes. Inherited by a junction's own boundaries and tested there since M4.1 checkpoint 5, which closes checkpoint 3's inherited-but-untested note: a dropping buffer written immediately below a row-building junction is that junction's output channel, so the policy answers the junction's own offer — the pump keeps building rows while the sink is held rather than being paced by it, and every row is accounted for as delivered or counted as dropped. A failing one faults the run with `BufferOverflowException` raised at that offer. An overflow policy on a balance's leg remains unreachable by construction and is recorded as such rather than tested. |
| Operator fusion | P1 | M2 | Implemented | Compatible adjacent stages share an executor without changing element semantics. |
| Explicit async boundary | P1 | M2 | Implemented | The spelling is `Buffer(options)`, not an Akka-style `.Async()` marker, and that is a decision rather than a gap: a boundary that carries no declared capacity and no declared overflow policy would be a concurrency change with an implicit queue, which is the one thing this engine refuses to have. A declared buffer cuts fusion and gives the stage below its own segment and thread — visible in the plan since M2, measured across the DAG since M4.1 (fusion survives inside junction-free branches and stops at every declared boundary), and priced explicitly where an operator implies one (`GroupedWithin` documents that its clock-closed batch costs a boundary; a fused count-closed batch does not). Ordering across a boundary is the channel's FIFO and is part of the boundary tables in LOCAL-RUNTIME.md. |
| Credit protocol across Orleans boundaries | P0 | M3 | Implemented | A call in flight is credit spent and its reply is the grant; nothing on the wire carries credit. Neither an awaited grain call nor a stream publication is counted as downstream demand: each adapter's bound is what admits the next element. |
| Partition-aware placement | P1 | M3 | Research | Partition ownership, rebalance, ordering, and failover are specified. Half of it exists on `main` and the row does not advance on half: placement of run grains and per-key executor grains is a hosting option (cluster default, random, prefer-local, hash-based) and per-key ordering is proven, while ownership, rebalance, and cross-silo keyed evidence are a recorded M3 deferral (see the roadmap) and a single-silo suite cannot show where activations landed. |
| Pause, resume, drain, shutdown, and abort | P1 | M2 | Implemented | Each control has distinct state transitions and in-flight behavior. Proven across branching topologies since M4.1 checkpoint 5, and per junction rather than in general: a pause reaches quiescence on a partition **holding an element it has already routed**, a broadcast that cannot pull because one leg is full, a balance with no willing leg, a concat asleep on the input whose turn it is while another has one ready, a merge asleep on every input, a zip holding a column, a combine-latest remembering every input's latest, and a loop with its own stream circulating — and every one of them resumes with what it held delivered once, unchanged, and in order. The held states are reachable only because a sink probe stops a consumer inside one of the runtime's own waits rather than inside an author's callback, which blocks quiescence by design. The M2 quiescence counters needed no change for junctions — they count segments and callbacks, and a junction is a segment — but the claim they rest on did not hold: a channel sink's write into a full channel reported nothing, so a run holding an element there could never quiesce and `PauseAsync` hung rather than failed. Fixed by the bracket every other wait already had; the hole was never junction-specific and its regression lives with the linear suite. Resume-then-repause storms on a diamond and on a graph mixing partition, merge, broadcast, and zip neither deadlock nor lose, duplicate, or reorder an element. The per-junction memory bounds of ADR 0005 are asserted *through* a pause: one element for a partition (with the sibling leg starving for exactly as long), none for a broadcast or a merge that is waiting rather than placing, N−1 columns for a zip, N for a combine-latest. |
| Kill switch and external shutdown control | P1 | M2 | Implemented | Single-run control is a RunHandle intrinsic (ADR 0004): shutdown drains, disposal cancels; a switch shared across runs is a separate documented contract. The drain-versus-abandon split is proven across branching topologies since M4.1 checkpoint 5, on one graph in one held state so that the two differ by nothing but the request: a diamond holding its first row delivers everything it admitted under shutdown and only the row already inside the author's callback under cancellation, and a graph mixing a partition, a merge, and a declared buffer drains all of it. What "admitted" means is exact rather than estimated, because an emit into a source probe completes when the run has taken the element. Disposal mid-flight is asserted once per junction kind and once for a cycle, and the load-bearing claim is that it *returns* — it waits for every segment to leave its loop, so a pump that could not be woken from its own wait would hang rather than fail — with the outcome cancelled, every enumerator released including the per-lap ones an endless source hands out, and a second disposal changing nothing. |

## Lifecycle and failure

| Capability | Tier | Target | Status | Required semantic proof |
|---|---:|---:|---|---|
| Completion propagation | P0 | M2 | Implemented | Downstream completion and upstream resource release are deterministic. |
| Failure propagation | P0 | M2 | Implemented | Downstream receives failure; upstream receives cancellation unless recovery intercepts it. Proven *sideways* since M4.1 checkpoint 5, which is the statement a graph adds to a chain: a failure on one leg of a fan-out reaches the sibling leg as cancellation and not as an ordinary end, proved by an asynchronous callback on that branch holding the run's own token and recording which of the two it observed. ADR 0005's first shared rule — an input's failure fails the run whether or not that input was being read — was already proven across a fan-in by checkpoint 2. |
| Downstream cancellation | P0 | M2 | Implemented | Early sinks cancel upstream and release resources. |
| Cancellation of async work | P0 | M2 | Implemented | Stage cancellation reaches `Task`, `ValueTask`, and later F# `Async` adapters. |
| Supervision: stop | P1 | M5 | Implemented | The failing stage fails the defined section or graph. **This row is the default and it flipped by being contrasted rather than by being built**: M5.1 added the declared exceptions, so "a failure fails the run" is now a statement with an edge, and the edge is what the suite asserts. One graph with an injected failure inside a supervision scope's chain and one with the same failure a stage earlier — identical in source, arming, and sink — end contained and failed respectively (`SupervisionBoundaryTests`), and the same holds a stage *below* a scope and on a junction leg beside one (`SupervisionCompositionTests`). Two more edges are asserted rather than assumed: a cancellation is not a failure and no policy weakens it, and a failure of the machinery — a payload the runtime cannot read, a chain holding a shape a scope cannot execute, two planes describing different chains — is refused at materialization, before the run has an element to supervise. A failure raised while a stream is *ending* is also unsupervised and is stated as v1's honesty: the residue walk has no failing element to drop and nothing to re-offer, and inventing an answer for one would be inventing semantics. |
| Supervision: resume | P1 | M5 | Implemented | The failing element is dropped while compatible stage state is retained. **Proved by values rather than by counts**, which is the only proof that separates it from the row below: `Source.Supervised(new SupervisionOptions { Form = SupervisionForm.Resume }, flow)` over `[1,2,3,4]` with the second element failing inside the scope and a `Scan` after the fault point produces `[1, 4, 8]` — the running sum never saw the dropped element and never restarted (`SupervisionTests`). A half-filled batch inside the scope stays open across the failure, asserted on the same graph. The drop is **counted and not silent**: `RunHandle.SupervisedFailures` moves once per failure a scope intercepted, internal for the reason `DroppedElements` is internal — what an author reads it through is the monitor, which arrived in M5.5 as `RunHandle.Snapshot()`. The scope's chain and the policy are both in the document (`local-supervision-parameters@v1`), so two scopes with different forms have different fingerprints; no form names an exception type, and that is a recorded deferral rather than an oversight (ADR 0007). |
| Supervision: restart stage | P1 | M5 | Implemented | The failing element is dropped and declared local stage state resets. **The same graph as the row above, one enumeration member apart, producing `[1, 3, 7]`**: the scan returns to its seed, and the pair is what makes each form's semantics exact rather than plausible (`SupervisionTests`). What "reset" means is exact because the chain is declared — a batch abandons its open group, asserted by the elements that then never arrive — and it is the group-by's own per-key instantiation machinery reused: every stage is rebuilt from the very factory a fresh run builds it from. A fault point's arrival counter deliberately survives a restart, because it is the test's accounting rather than the author's state. |
| Retry element | P1 | M5 | Implemented | Attempt count, backoff, idempotency, and poison-element handling are explicit. All four are in the document or in a counter. **Attempts** are `MaxAttempts`, counted including the first. **Backoff** is an explicit `TimeSpan` ladder (`backoffTicks`) whose last rung repeats and whose empty form retries at once, measured on a `TestClock` to the tick — the run is advanced to one tick short of the rung, asserted to have done nothing, and then advanced the last tick (`SupervisionCompositionTests`). **There is no jitter in v1** and the reason is recorded: jitter spreads a fleet's restarts and a per-element retry inside one run has no fleet, and a random source would make "the waits are exactly what the document says" a statistical claim instead of an asserted one; the ladder's shape admits jitter later without a document change. **Idempotency is the author's, and the engine states why**: a retry re-offers the element to the scope's *first* stage, so a stateful stage inside a retrying scope sees the element once per attempt — asserted by value, not footnoted — which is why the exhaustion answer can escalate to `RestartStage`. **Poison elements** are counted as such in `RunHandle.PoisonElements`, beside `SupervisedFailures` because the two answer different questions; the three exhaustion answers (fail the run with the last attempt's own exception, escalate to resume, escalate to restart) each have their own test. Pause, shutdown, and cancellation during a backoff wait are asserted on the controlled clock and follow the checkpoint-5 wait discipline unchanged. |
| Recover with element or alternate source | P1 | M5 | Implemented | Completion after fallback and source-switch boundaries are distinct. **The first half is code and the second is a decision, and the row says which is which.** `Supervised(options, scope, fallback)` with `SupervisionForm.Recover` emits the declared fallback and ends the scope's stream *successfully*: everything above the scope stops, everything below it drains, the result slot resolves rather than faulting, and the run reports success — asserted both as the element sequence and as a fold's resolved value (`SupervisionTests`). The fallback is a constant in the binding table rather than in the payload, because a local document names no element type; ADR 0007's canonical-constant half of that split belongs to the registered vocabulary, where element contracts are real. **Recovering with an alternate source is deliberately not a knob on this scope and is not implemented**: switching sources is a decision about a section of the graph rather than about one stage's stream, it belongs to the restart-section row below, and keeping the two boundaries distinct is exactly what this row demands. |
| Restart source/flow/sink section with backoff | P1 | M5 | Research | Reset scope, jitter, restart budget, and in-flight loss window are documented. **The M5 exit verdict is a recorded deferral, and the reason is that this form is new design rather than a missing composition.** The four shipped forms supervise a *flow chain* — the scope-as-stage machinery wraps element stages, and everything about reset, retry, and recover is stated over that chain. A restart *section* is the coarser grain: a scope that contains a **source** (or a sink), a restart *budget* with backoff and jitter across attempts, and an in-flight loss window per restart. A source inside a scope changes what reset means — a cursor's position, an adapter's subscription, and a section's buffered elements all have to be given semantics the flow-scope forms never needed — and ADR 0005's herd note marks this row as where the thundering herd is real. Recovering with an *alternate source* is the same boundary and rides with it (its row says so). Nothing shipped blocks it: the scope machinery, the budget arithmetic of the retry form, and the injection seam are the parts it would be built from, and the design owes its own evidence when a deployment demands the form. |
| Durable resume after process/silo failure | P1 | M5 | Qualified | Checkpoint, source cursor, sink commit, and replay semantics are proven together, **now across a silo dying as well as inside one process**. The row is written in two parts because the two halves prove different things and were built a phase apart. M5.2 implements and proves the *model*, in one process: a checkpoint is a canonical document carrying ADR 0007's five parts with a writer, a strict reader, and a golden test over the bytes; the store is the coordinator's ETag shape generalized (`ICheckpointStore`, keyed by graph and run), and a superseded writer's capture is refused with `CheckpointConflictException` which kills the stale attempt rather than being retried; the timing is declared (`DurableRunOptions`, an interval on the run's clock and/or an every-N-elements bound, and **a run declaring neither never touches the store**, asserted against the store); a capture is taken at the pause machinery's own safe points — hold, snapshot, resume — with the cost stated and measured (`RunHandle.CheckpointHold`) rather than assumed away, and a capture is proven to lose and duplicate nothing by being taken. Three seams put something in a checkpoint: a **cursor** (`from-enumerable` gains an index cursor; every other local source declares none and resumes from now, stated per source in `ADAPTERS.md`), a **durable scope** (`local/durable@v1`, requiring the M0 `durable-state` token, whose chain holds only stages whose state is a canonical value and which refuses every other shape by name), and a **commit mark** (a marking sink whose mark advances *after* the side effect). The local resume proof is exact: a run crashed by an injected fault at element nine, checkpointing every three, stores cursor six; the resumed materialization reopens the source there, restores the durable running total to twenty-one, resets the scan outside the scope to its seed (proved by values, not counts), and the sink replays exactly the two elements between the stored cursor and the mark at the crash. A resume against a different fingerprint or revision is refused by name — v1 is same-revision only. **The loss window is measured too**: a batch outside a durable scope holds elements the cursor has counted and the mark has not, and a resume drops exactly `cursor − committed` of them, which the checkpoint itself says because it carries both numbers. **M5.3 is the other half and it is here.** A silo now hosts durable runs: the store is registered on the silo (`UseCheckpointStore`, no default, because an in-memory default would let a deployment believe its runs were durable), the coordinator persists one record per *declared* durable run — the document, the timing, the epoch — which is what the phase-1 note meant by "M5's durable resume will persist what reconciliation actually reads", and **resume is activation-driven with no second protocol**: a run grain that finds a checkpoint when it activates claims a fresh epoch, materializes from that position, and reports Running, so the client's own status poll is the trigger and `PipelineRunLostException` becomes unreachable for such a run. A durable run with no checkpoint yet is a lost attempt exactly as an ordinary one is, asserted rather than footnoted. **The run identity becomes the author's**, which is the phase's one API-semantic change: two durable materializations under one name are one run, and a name already holding a different document is refused by name with both fingerprints on the exception. **The crash evidence, on a three-silo fixture, is by value.** Five elements with a capture every three, the hosting silo killed: the store holds cursor three, the sink's log is `[1,2,3,4,5]`, and after the kill the resumed attempt on a surviving silo makes it `[1,2,3,4,5,4,5]` — the duplicate window is exactly the two elements between the stored cursor and the crash. Two thousand elements at a capture per element, killed three times: every stored document still reads and names this graph, the union of the attempts covers the stream with no gap, and the total delivered is between 2000 and 2003 — **at most one replayed element per kill**, an arithmetic consequence of the bound. A superseded writer's capture is refused with `CheckpointConflictException` and kills that attempt (staged with the store's `Supersede`, because Orleans permits only one activation per run). The contrast holds: the same pipeline through the same kill, not declared durable, still reports `PipelineRunLostException` with nothing in the store. **And the cursor the model was designed for shipped**: `orleans/stream-source` stores the sequence token of the element the run delivered and a resumed subscription reopens at it, with two probed facts stated rather than assumed — rewind is *inclusive* of the element the token names, so a stream source's window is one element wider than an index cursor's, and the memory provider purges its cache when its last consumer leaves, so `IsRewindable` is ability rather than retention. **What is still not proven** is listed in ORLEANS-RUNTIME.md's M5.3 limits and three of them bear on this row: a capture cannot be taken while a source is inside its own step (a quiet stream delays a timed capture — measured, both halves); the suite's store lives in the test process and therefore cannot be torn by a silo dying, so a real store's write atomicity is stated by the contract and not exercised; and a durable run is continued by the next activation whatever ended the previous attempt, because a checkpoint says where and never whether — so a completed or failed durable run that loses its activation is resumed and runs its tail again. **M5.4 closes the last of those three and leaves the other two standing.** A checkpoint still says only where; what says *whether* is the coordinator's register, which an ending is now reported to — the attempt tells its coordinator the terminal state it reached, the declaration records it, and a later claim answers with the ending instead of a document to continue. The pinned `…, 4, 5, 5` becomes `…, 4, 5`, and a failed durable run reports the same failure back rather than faulting a second time (proved by the log rather than by the exception: a re-run would have replayed the element between the cursor and the fault). **Completing and failing end a run and cancelling does not**, because a deactivation cancels the run it was hosting — asserted through an ordinary handle disposal, which is continued by the next activation exactly as a crash is, and refused by name at the coordinator. **The checkpoint of a finished run is kept, not cleared**: the declaration is what retires the run, and where it got to is the question asked afterwards, so forgetting the position stays explicit. The report carries the reporting attempt's epoch and is fenced by it, so a superseded attempt finishing late cannot retire somebody else's run (staged directly, with the declaration proved still open by a continuation that replays its window); and a status poll that observes a terminal state awaits the report before answering, so a caller that has seen a durable run end has seen a run the register already records as ended. What this does **not** close: a silo that dies between the run ending and the report landing loses the report, and that run is resumed once by a later activation — M5.3's behaviour for that one run, and the honest residual of two separate writes. **M5.5 closes the last flagged blocker and the row advances to Qualified on it.** The registered-sink commit half was the one seam the M5.3 judgment named as missing: the terminating grain call now declares a mark — `{"acknowledged":n}`, advanced after the awaited reply and never before, restored across a resume — and the crash suite measures the pair by value on a pipeline with both halves: killed at a gated element with captures every three, the stored pair reads cursor 6 / mark 5 (the lag is the one call in flight at a bound of one), the resumed log duplicates exactly the elements after the stored cursor, and the final mark undercounts by the acknowledgement the first attempt received after its last capture — the direction the seam is built to fail in, because undercounting widens a replay and can never narrow one. With that in, contract tests (the golden checkpoint document, the store's ETag contract, the wire round-trip of every status member), failure tests (single kills, repeated kills with no torn document, staged supersede, the no-checkpoint and non-durable contrasts, the lost-report residual), and integration (activation-driven resume on a three-silo fixture, rolling upgrade, replacement, the stream cursor's inclusive rewind) prove the documented behavior at every boundary the documents claim — including the limits, which are documented as limits. **What qualification does not cover, named rather than implied**: the suite's store lives in the test process, so a production store's write atomicity and conditional-write refusal are held by the stated `ICheckpointStore` contract rather than exercised against a real backend; and a capture still cannot be taken while a source is inside its own blocking step. |

| Checkpointed stage state | P1 | M5 | Implemented | Schema version, atomicity boundary, and migration policy. **All three have an answer and one of them is a deferral said out loud.** The *schema* is a canonical document whose five members are always present and whose reader refuses a member it does not declare, with a golden test over the bytes; a stage's own state is written by that stage in a grammar of its own (`{"remaining":n}` for a take and a skip, `{}` for a stage holding nothing, and whatever the author's codec writes for a scan), and a durable scope's export is positional over its declared chain. The *atomicity boundary* is one document per `(graph, run)` written under one ETag at one quiescent point, so a checkpoint's cursor, its scope states, and its marks all describe the same moment — which is what makes a replayed element enter a durable scope's state exactly once. The store is emptied *before* the register is rewritten, which makes a half-finished replacement safe to retry: cleared-then-not-recorded restarts a run its own at-least-once contract already admits, while recorded-then-not-cleared would leave a declaration naming one document beside a checkpoint of another. | Rolling upgrade/catalog negotiation | P1 | M5 | Implemented | A run never executes an incompatible stage catalog silently. **Proved at both moments a document meets a host, and the second one is what M5.4 added.** At a *start*: a coordinator validates against its own silo's catalog and refuses by name with the whole diagnostic report, a run grain validates again against *its* host's because acceptance by a coordinator is not a promise about where the run will execute (asserted over twenty placements on a two-silo mixed-catalog fixture, both outcomes required to occur), and every accepted start reports the validating silo's `CatalogFingerprint` on its ticket — which is the only signal a client gets that its runs are not all being checked against one vocabulary, asserted by two silos answering differently for one document both accept. What is not here: no per-scope dimension (the M5.1 deferral, visible in the instrument set on purpose), no run-id metric tag ever, and the ended counter counts observed endings — a process dying mid-settle counted nothing, which is the two-writes honesty again. |
| Stage/run monitor snapshots | P1 | M5 | Implemented | `RunHandle.Snapshot()` and `OrleansRunHandle.SnapshotAsync()` (M5.5): one reading of status (`Running`/`Completed`/`Failed`/`Canceled` — four members where `RunEndingKind` has two, because a snapshot answers *where is it* and an ending answers *how did it end*) plus the five counters the run already keeps — dropped elements, supervised failures, poison elements, checkpoints written, total checkpoint hold. **The honest v1 shape the earlier rows kept pointing at**: a reading of existing state, no new instrumentation inside any stage, not a consistent cut (counters are read one after another while the run moves; each number exact), stable forever once the run ends. Per-*scope* observability — which scope dropped what — remains the recorded M5.1 deferral and the type's own documentation says so. Over the wire the counters ride the status snapshot (five new `[Id]` members filled by the run grain from the engine it hosts) and **describe the answering attempt**: a durable ending re-read after its reporting activation died comes from the coordinator's register, which records outcomes and not diagnostics, so those counters read zero — the register stays a fenced outcome protocol on purpose, and history belongs to the meter, which was fed continuously while the attempt lived. A run reported `NotStarted` throws `PipelineRunLostException` rather than inventing a reading. **Two counter boundaries found by testing and recorded rather than hidden**: `DroppedElements` covers engine-owned boundaries only — an adapter's private ingress (stream/broadcast/observer/reminder) counts its drops internally and no seam folds them in yet (verified by measurement: two dropped pushes, a reading of zero); and `SupervisedFailures`/`PoisonElements` are structurally zero in pipelines, because supervision is `local/*` vocabulary and `Nondeployable`. Both deferrals are stated on the snapshot type and in ORLEANS-RUNTIME's M5.5 limits. |
